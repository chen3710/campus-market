# 校园二手交易平台 · 面试讲点

这份文档是给你面试用的。核心思路是：**不要背功能列表，要把面试官往你会的地方引。**

下面每个点都按「面试官可能怎么问 → 你怎么答 → 他可能追问什么 → 怎么接」来组织。

---

## 0. 开场：30 秒讲清这个项目

> 我做了一个校园二手交易平台，技术栈是 Spring Boot 3 + MyBatis-Plus + MySQL，前端用原生 HTML/CSS/JS，前后端由同一个应用提供。
>
> 选这个题目的原因是它有一条完整的业务闭环：用户发布商品 → 买家下单 → 卖家确认 → 面交完成 → 双方信用分变化。这条链路里天然包含三类值得深挖的技术问题：**并发下的商品归属争抢、订单的状态流转、以及多角色的数据权限隔离**。我在项目里针对这三点分别用了 CAS 原子占位、状态机模式、以及基于注解的拦截器方案来解决。

说完这段，面试官大概率会顺着这三个点问下去——而这三个点你都准备好了。

## 1. 防超卖：为什么不是「先查询再更新」

**面试官问**：如果两个人同时下单同一件商品，怎么保证只有一个人成功？

**❌ 先说错误做法**（先讲错再讲对，显得你是想过的，不是背的）：

```java
Product p = productMapper.selectById(id);
if (p.getStatus().equals("ON_SALE")) {   // ← 两次操作之间有竞态窗口
    p.setStatus("LOCKED");
    productMapper.updateById(p);
}
```

问题在于 `SELECT` 和 `UPDATE` 之间存在时间窗口。两个线程可能**都**读到 `ON_SALE`，然后**都**去更新，结果两个订单都创建成功，商品被卖了两次。

**✅ 正确做法**：把「判断」和「更新」压缩成一条 SQL。

```sql
UPDATE product
SET status = 'LOCKED', version = version + 1
WHERE id = ? AND status = 'ON_SALE' AND version = ?
```

然后判断影响行数：

```java
int locked = productMapper.casUpdateStatusWithVersion(id, "ON_SALE", "LOCKED", product.getVersion());
if (locked == 0) {
    throw new BusinessException(ResultCode.CONFLICT, "手慢了，该商品已被抢先下单");
}
```

**为什么这样是对的**：InnoDB 执行 `UPDATE ... WHERE id = ?` 时会对这一行加**排他锁**。
并发的第二个事务会阻塞等待；等第一个事务提交后，第二个事务做的是**当前读**（不是快照读），
此时 `status` 已经是 `LOCKED`，`WHERE` 条件不成立，影响行数为 0 → 下单失败。

这就是 **数据库行锁 + CAS（Compare And Swap）** 实现原子占位。

**追问 1：为什么还要带 `version`？只判断 `status` 不够吗？**

> 对防超卖来说，只判断 `status` 已经足够了。带 `version` 是更严格的乐观锁语义：它额外保证了"我读到的商品信息（价格、标题）和我下单时用的信息是一致的"。
> 如果在我读到商品之后、下单之前，卖家改了价格，`version` 会变，CAS 就会失败，避免我以旧价格下单。
> 这里我把两种机制的意图都表达了：`status` 管业务状态，`version` 管数据版本。

**追问 2：那和悲观锁 `SELECT ... FOR UPDATE` 有什么区别？怎么选？**

> `FOR UPDATE` 是悲观锁：先加锁再操作，阻塞其他事务，冲突多的时候会有大量等待和死锁风险。
> CAS 是乐观锁思路：不加锁，靠条件更新，冲突时直接失败让用户重试。
> 二手交易这种"一件商品只有一个买家"的场景，**冲突其实很低频**，用乐观锁更划算。
> 如果是秒杀那种极端场景，反而应该用 Redis 预扣减 + 消息队列异步下单，把流量挡在数据库前面。

**追问 3：为什么把整个下单流程放在 `@Transactional` 里？失败了商品会不会一直是 LOCKED？**

> 会回滚。`create` 方法标了 `@Transactional(rollbackFor = Exception.class)`，如果后续 `insert` 订单失败，前面那次 CAS 更新会被一起回滚，商品回到 `ON_SALE`，不会出现"锁死了但没订单"的脏数据。

## 2. 订单状态机：为什么不用一堆 if-else

**面试官问**：订单有几种状态？状态之间怎么流转？

**答**：四个状态，我把它收敛成了一个枚举 + 一张流转表。

```
CREATED（待卖家确认） ──卖家确认──> CONFIRMED（待面交） ──买家完成──> FINISHED（终态）
        │                                   │
        └────────── 买家/卖家取消 ───────────┴──────────> CANCELLED（终态）
```

实现上，`OrderStatus` 枚举里维护一张 `Map<当前状态, Set<可流转状态>>`：

```java
static {
    TRANSITIONS.put(CREATED,   EnumSet.of(CONFIRMED, CANCELLED));
    TRANSITIONS.put(CONFIRMED, EnumSet.of(FINISHED, CANCELLED));
    TRANSITIONS.put(FINISHED,  EnumSet.noneOf(OrderStatus.class));
    TRANSITIONS.put(CANCELLED, EnumSet.noneOf(OrderStatus.class));
}

public void assertTransferTo(OrderStatus target) {
    if (!canTransferTo(target)) {
        throw new BusinessException("订单状态不允许从「" + this.desc + "」变更为「" + target.desc + "」");
    }
}
```

**这样做的收益**：

1. **规则集中在一处**。新增状态（比如加一个"待付款"）只改这张表，不用去翻各个 Service 找散落的 `if`。
2. **非法流转自动被拦**。比如"已取消的订单又被确认"，业务代码里根本不需要写这个判断。
3. **前端不用抄逻辑**。订单 VO 里我返回了一个 `actions` 字段，由状态机推导出"当前用户在当前状态下能做什么"，前端照着渲染按钮就行。**状态判断只有一份，不会前后端不一致。**

**追问：状态更新会不会有并发问题？比如买卖双方同时点了取消和确认？**

> 会。所以订单状态更新也是 CAS：
> ```java
> orderMapper.update(null, new LambdaUpdateWrapper<ProductOrder>()
>     .eq(ProductOrder::getId, orderId)
>     .eq(ProductOrder::getStatus, from.name())   // ← 关键：带上当前状态做条件
>     .set(ProductOrder::getStatus, target.name()));
> ```
> 如果影响行数为 0，说明状态在我读取之后已经被别人改了，抛 409 让前端刷新。

## 3. JWT 鉴权：为什么不用 Spring Security

**面试官问**：登录鉴权怎么做的？

**答**：JJWT + 自定义拦截器 + 注解，没有引入 Spring Security。

**JWT 为什么是无状态的**：服务端用密钥对 `header.payload` 签名，Token 本身携带用户身份（我把用户 ID 放 `subject`，用户名和角色放自定义 claim）。服务端只需要验签，**不需要存 Session**。所以水平扩容时不需要 Redis 做 Session 共享，多个实例都能独立校验。

**拦截器怎么判断该不该拦**：按**注解**驱动，不是按 URL 白名单。

```java
boolean needLogin = hasAnnotation(handlerMethod, LoginRequired.class);
boolean needAdmin = hasAnnotation(handlerMethod, AdminOnly.class);
if (!needLogin && !needAdmin) return true;
```

`@LoginRequired` / `@AdminOnly` 可以加在方法上，也可以加在 Controller 类上（比如 `AdminController` 整体加了 `@AdminOnly`）。

**为什么用注解而不是 URL 白名单？**
> 白名单是"默认放行 + 手工排除"，新增接口时如果忘了往白名单里加，接口就直接裸奔了——这是很常见的安全事故。
> 注解是"默认放行 + 显式声明需要鉴权"，虽然也需要记得加注解，但它的心智负担更低，而且**在代码里一眼能看出这个接口要不要登录**。

**校验顺序**：先认证（解析 Token 得到身份）→ 再鉴权（判断角色是否满足）→ 最后写入上下文。

```java
LoginUser loginUser = jwtUtil.parse(token);        // 认证
if (needAdmin && !loginUser.isAdmin()) {           // 鉴权
    throw new BusinessException(ResultCode.FORBIDDEN, "该操作仅管理员可用");
}
UserContext.set(loginUser);
```

**追问 1：ThreadLocal 用完不清理会怎样？**

> 会串号。Tomcat 的线程是复用的，如果不清理，下一个请求复用同一个线程时可能读到上一个用户的信息——这是非常严重的安全问题。
> 所以我在 `afterCompletion` 里无条件 `UserContext.clear()`。另外我特意把 `UserContext.set()` 放在**鉴权通过之后**，因为 `preHandle` 抛异常时 `afterCompletion` 不会执行（只有 `preHandle` 返回 true 的拦截器才会走 `afterCompletion`）。

**追问 2：Token 泄露了怎么办？JWT 没法主动失效吧？**

> 这是 JWT 的固有短板。业界常见方案是：
> 1. **双 Token**：Access Token 短有效期（比如 30 分钟），Refresh Token 长有效期且存库，可以主动吊销。
> 2. **黑名单**：登出时把 Token 的 `jti` 写进 Redis，校验时查一下，代价是失去了无状态性。
> 3. **版本号**：用户表加一个 `token_version`，改密码时 +1，Token 里带上这个版本，不一致就拒绝。
> 我这个项目是课程作品，用的是单一长有效期 Token，生产环境我会改成双 Token 方案。

**追问 3：前端 Token 存 localStorage 还是 Cookie？**

> 我存了 localStorage。好处是简单、天然免疫 CSRF（因为不会自动携带）。
> 代价是**无法防御 XSS** —— 一旦页面被注入脚本，Token 就能被读走。
> 所以严格来说，更稳的方案是 httpOnly + Secure + SameSite 的 Cookie 配 CSRF Token。
> 我在项目里对用户输入做了转义（前端的 `escapeHtml`），算是补了一道防线。

**追问 4：密码怎么存的？**

> BCrypt，不是 MD5/SHA。
> 三个原因：
> 1. **自带随机盐**，同一个密码两次加密结果不同，攻击者无法用彩虹表批量反查。
> 2. **计算成本可调**（我设的 strength = 10），故意让它慢，暴力破解的成本被拉高。
> 3. **不可逆**，只能 `matches()` 校验，不能解密。
>
> 另外我用了 `@JsonIgnore` 标注密码字段，防止任何接口在返回实体时不小心把哈希带出去。
>
> 还有一个细节：登录时"用户不存在"和"密码错误"我返回了**完全相同**的提示，避免攻击者通过错误信息枚举出系统里存在哪些账号。

## 4. N+1 查询：列表页最容易踩的坑

**面试官问**：商品列表要显示卖家昵称和分类名，怎么查的？

**答**：用一次 `LEFT JOIN` 全查出来，不是循环里逐个查。

```sql
SELECT p.*, c.name AS category_name,
       u.nickname AS seller_nickname, u.campus AS seller_campus
FROM product p
LEFT JOIN category c ON c.id = p.category_id
LEFT JOIN `user` u ON u.id = p.seller_id
WHERE p.deleted = 0
```

**如果不用 JOIN 会怎样**：查出 12 条商品后，循环里给每条商品查一次卖家、查一次分类 —— 12 条数据就是 1 + 24 = 25 次查询。数据量一大就是灾难，这就是典型的 **N+1 问题**。

**还有一处也做了优化**：商品列表要显示"当前用户有没有收藏过"。做法是把这一页所有商品 ID 收集起来，用一次 `IN` 查询捞出收藏关系，在内存里做匹配：

```java
Set<Long> favoritedIds = favoriteMapper.selectList(new LambdaQueryWrapper<Favorite>()
        .select(Favorite::getProductId)
        .eq(Favorite::getUserId, viewerId)
        .in(Favorite::getProductId, productIds))   // ← 一次 IN，而不是循环
    .stream().map(Favorite::getProductId).collect(Collectors.toSet());
```

订单列表、留言列表也是同样的思路：`selectBatchIds` 一次把用户捞回来，再在内存里拼装。

**追问：为什么不用 MyBatis 的 `<collection>` 嵌套映射？**

> 嵌套映射也能解决 N+1，但会把返回结构变复杂（一个 Product 里套一个 Seller 对象），
> 而且分页插件和嵌套集合一起用的时候容易出问题。
> 我这里用平铺的 VO + 手动组装，结构更可控，也更容易做缓存。

## 5. SQL 注入：ORDER BY 是个特殊的地方

**面试官问**：你的搜索支持排序，排序字段是前端传的，怎么防注入？

**答**：**排序字段不能用 `#{}`，因为 `#{}` 是预编译占位符，只能用在"值"的位置，不能用在 SQL 关键字（表名、列名、ORDER BY 方向）的位置。**

所以我用 MyBatis 的 `choose/when` 做**白名单枚举**：

```xml
ORDER BY
<choose>
    <when test='query.sort == "priceAsc"'>p.price ASC, p.id DESC</when>
    <when test='query.sort == "priceDesc"'>p.price DESC, p.id DESC</when>
    <when test='query.sort == "hot"'>p.view_count DESC, p.id DESC</when>
    <otherwise>p.create_time DESC, p.id DESC</otherwise>
</choose>
```

前端传什么进来，只会落到这四个分支之一，其余一律走默认排序。**永远不要把前端字符串直接拼进 SQL。**

顺带一提，`p.id DESC` 这个第二排序键不是随便加的：`create_time` 有可能重复（同一秒发布多件），加上主键能保证**分页结果稳定**，否则翻页时可能看到重复或漏掉的数据。

## 6. 为什么不用 `@Autowired` 字段注入

代码里统一用 `@RequiredArgsConstructor` + `final` 字段：

```java
@Service
@RequiredArgsConstructor
public class OrderServiceImpl implements OrderService {
    private final ProductMapper productMapper;
    private final UserMapper userMapper;
}
```

**好处**：
1. **依赖不可变**。`final` 保证注入后不能被改。
2. **启动即暴露问题**。字段注入是运行时才注入，构造器注入在容器启动时就会因为缺少 Bean 而失败，问题暴露得更早。
3. **方便测试**。可以直接 `new OrderServiceImpl(mockProductMapper, ...)`，不需要起 Spring 容器。
4. **避免循环依赖被隐藏**。字段注入允许循环依赖（Spring 用三级缓存兜住），构造器注入会直接报错——早报错比晚报错好。

## 7. 全局异常处理

**面试官问**：Service 层抛异常，怎么保证前端拿到的格式是统一的？

**答**：`@RestControllerAdvice` 兜住所有异常。

```java
@ExceptionHandler(BusinessException.class)
public Result<Void> handleBusiness(BusinessException e) {
    return Result.fail(e.getCode(), e.getMessage());
}

@ExceptionHandler(MethodArgumentNotValidException.class)  // @Valid 校验失败
@ExceptionHandler(DuplicateKeyException.class)            // 唯一索引冲突
@ExceptionHandler(Exception.class)                        // 兜底，记 error 日志
```

**设计取舍**：业务异常打 `warn` 日志（预期内的，不用惊动），未预期异常打 `error` 并带堆栈（需要排查）。

**追问：为什么业务异常的 HTTP 状态码还是 200？**

> 这是个约定问题。我认为"用户名已存在"不是 HTTP 层面的错误，请求本身是被正确处理了。
> 如果混用 HTTP 状态码，前端要在 axios 的 catch 分支里处理业务错误，很别扭。
> 所以我统一返回 200，用响应体的 `code` 表达业务结果，前端只判断 `code === 200`。
> 当然也有团队坚持用 4xx/5xx，两种做法都能接受，关键是**全项目一致**。

**追问：那 `code` 字段内部怎么划分的？**

> 我分得比较细，因为混用会让排查问题时误判严重程度：
>
> | code | 含义 |
> |---|---|
> | 400 | 参数校验失败 |
> | 401 | 未登录 / 凭证失效 |
> | 403 | 无权限 |
> | 404 | 资源不存在 |
> | 409 | 状态冲突（商品被抢、重复注册） |
> | **422** | **业务规则不允许（订单状态非法流转、封禁管理员）** |
> | 999 | 系统异常，兜底 |
>
> 特别说一下 422：一开始我把所有业务异常都归到 500，后来发现"订单已取消不能再次确认"和"数据库连不上"返回同一个码，排查时根本分不清哪个是 bug。
> 改成 422（Unprocessable Entity：请求本身合法，但业务规则不允许）之后，看日志就能立刻区分。

## 8. 唯一索引 vs 应用层查重

**面试官问**：注册时怎么防止用户名重复？

**答**：**两层防护，但真正兜底的是数据库唯一索引。**

```java
Long exists = userMapper.selectCount(...eq(User::getUsername, username));
if (exists > 0) throw new BusinessException("该用户名已被注册");   // 第一层：给友好提示
// 第二层：数据库 uk_username 唯一索引
```

**为什么两层都要**：应用层的"先查再插"在高并发下两个请求可能同时通过检查，然后都去插入。
这时数据库的 `uk_username` 唯一索引会拦住第二个，抛 `DuplicateKeyException`，被全局异常处理器转成"数据已存在，请勿重复提交"。

**面试时可以说的一句总结**：*应用层的检查是为了体验（友好提示），数据库的约束是为了正确性（最终防线）。永远不要用应用层检查来保证数据一致性。*

收藏功能也是同样的思路：`favorite` 表的 `uk_user_product` 唯一索引防止重复收藏。

## 9. 文件上传的安全处理

**面试官问**：图片上传怎么做的？有什么安全考虑？

**答**：三个要点。

1. **扩展名白名单**。只允许 `jpg/jpeg/png/gif/webp/bmp`，不接受 `.jsp`、`.sh` 之类的可执行文件。
2. **文件名完全由服务端生成**，格式是 `yyyyMMdd/UUID.扩展名`，**不使用用户传来的文件名**。这样从根本上杜绝了 `../../etc/passwd` 这类路径穿越。
3. **落盘前再校验一次**：把路径 `normalize()` 之后，检查它是否仍在上传根目录之内，双重保险。

```java
Path target = root.resolve(relative).normalize();
if (!target.startsWith(root)) {
    throw new BusinessException("非法的文件路径");
}
```

另外 Spring Boot 侧也限制了 `max-file-size: 5MB`，超限会抛 `MaxUploadSizeExceededException`，同样被全局异常处理器接管。

## 10. 怎么证明代码是对的：四层验证

面试官如果问「你怎么保证代码没问题」，别只说"我测过了"。给一个有层次、有取舍的回答：

> 我按「跑得越快、覆盖越窄的测试放越底层」来组织，一共四层。前三层都在 `./mvnw test` 里，一条命令跑完 53 项。

### 第一层：单元测试（25 项，毫秒级）

只覆盖**纯逻辑**——订单状态机、商品状态，以及超时取消里的竞争分支。它们没有 IO、没有 Spring 容器，跑一次不到 2 秒。

**为什么偏偏测状态机？** 因为它满足三个条件：① 是纯函数，测起来零成本；② 逻辑一旦改错，会造成线上数据状态错乱（比如已取消的订单又被确认）；③ 它是这个项目里唯一「规则复杂到值得写测试」的地方。其他 CRUD 代码测了也只是复述一遍 MyBatis 的行为，性价比低。

最有价值的一个测试是把**完整流转矩阵写死成一张表**：

```java
String[][] matrix = {
        //              CONFIRMED  FINISHED  CANCELLED  CREATED
        /* CREATED   */ {"Y", "N", "Y", "N"},
        /* CONFIRMED */ {"N", "Y", "Y", "N"},
        /* FINISHED  */ {"N", "N", "N", "N"},
        /* CANCELLED */ {"N", "N", "N", "N"}
};
```

这样将来有人改动 `TRANSITIONS` 里的规则，测试会**立刻失败并指出是哪一条被改了**，而不是等线上出问题。

一个细节：断言里我引用枚举自身的 `desc`，而不是硬编码「已取消」这种字面量——文案随时可能调整，引用 `desc` 才能既验证语义、又不会因为改文案而假失败。

### 第二层：接口层集成测试（28 项，MockMvc，JVM 内）

这一层补的是**前一层和下一层之间的空白**：

- 单元测试把 Mapper 全 mock 掉了，**碰不到拦截器、参数校验、全局异常处理**这些 Spring MVC 的基础设施；
- 而 shell 冒烟测试虽然能碰到，却要先启动应用、跑得慢，还得靠外部进程和端口。

`MockMvc` 在**同一个 JVM 里**直接调用 DispatcherServlet，把两者的短板都绕开了。跑在 `h2` profile 上，不依赖本机 MySQL，所以 CI 里也能跑。

它分两个文件，各管一件事：

**`ApiIntegrationTest`（21 项）—— 鉴权与状态码语义**

| 覆盖点 | 断言 |
|---|---|
| 鉴权 | 无 Token → 401；Token 被篡改 → 401；格式不对 → 401；普通用户访问管理端 → 403；管理员 → 200 |
| 「可选登录」降级 | 公开接口带一个**无效 Token** 时静默降级为匿名（200），而不是 401 |
| 参数校验 | 空标题 / 价格为 0 / 缺必填参数 / 请求体不是合法 JSON → 一律 400（**不是 500**） |
| 资源与冲突 | 商品不存在 → 404；用户名已注册 → 409 |
| 业务规则 | 非法状态流转 → 422；购买自己的商品 → 403；封禁管理员 → 422 |
| 响应契约 | **HTTP 状态码恒为 200**，成败由 body 里的 `code` 表达；`code`/`message`/`timestamp` 三件套始终存在 |
| 安全 | 响应体里**不出现 `password`**；密码错误与用户名不存在返回**完全相同的提示**（防账号枚举） |
| 全链路 | 注册 → 登录 → 访问受保护接口，一路打通 |

其中「**HTTP 恒 200**」那条特别值得讲：这是项目**刻意选择**的契约，前端只需判断 `code === 200`，不用同时处理两层状态码。用测试把它钉死，是为了防止将来有人「顺手」给异常处理器加上 `@ResponseStatus` 而悄悄破坏契约。

**`OrderTimeoutQueryIntegrationTest`（7 项）—— SQL 判定逻辑**

这一类是 Mockito **测不到**的：`selectTimeoutOrders` 的核心就是「CREATED 看 `create_time`、CONFIRMED 看 `confirm_time`」这条 SQL 条件，单测把它整个 mock 掉，等于什么都没验证。所以这里真的建表、真的插数据、真的跑一遍 SQL，用 `JdbcTemplate` 把时间戳改到过去来模拟「挂了很久的订单」（总比在测试里 sleep 半小时强）。

最值钱的一条是 `confirmedOrderJudgedByConfirmTime`：构造「很早下单、但卖家刚刚才确认」的订单，断言它**不该**被判超时。**用 `create_time` 判定的错误实现会在这里立刻失败**——这就是这条断言的唯一目的。

> 一个工程细节：这两个测试类刻意用**完全相同的一组注解**（`@SpringBootTest` + `@ActiveProfiles("h2")` + 同样的 `@TestPropertySource`），这样 Spring 会**复用同一个上下文**，省掉一次容器启动。都关掉定时任务（`app.order.enabled=false`），避免它在测试执行期间偷偷改订单状态导致断言飘忽。

### 第三层：冒烟测试（108 项断言，走真实 HTTP）

脚本 `scripts/smoke-test.sh` 打真实接口，覆盖的是前两层都碰不到的东西：**真实数据库的事务行为、真实 JWT 拦截器链路、真实 HTTP 状态码，以及并发**。

**最有说服力的一条**：10 个并发请求同时下单同一件商品，断言**恰好只有 1 个成功**。这是唯一能证明 CAS 防超卖真的生效的方法——单测测不出并发，MockMvc 是单线程的也测不出并发，手点更点不出来。

> 为什么有了 MockMvc 还要留着这层 shell 脚本？因为 MockMvc 用的是**内存里的假 Servlet 容器**，而冒烟测试打的是**真的 Netty/Tomcat、真的 MySQL**。像「数据库事务在真实连接池下是否如期回滚」这种问题，只有后者能暴露。两层不重复，是互补的。

### 第四层：前端无头浏览器验证

用系统自带的 Edge 无头模式渲染全部 6 个页面，抓 JS 运行时错误，断言**0 个错误**；同时验证 `admin.html` 对普通用户正确显示"没有访问权限"。零安装，不需要 Playwright。

### 顺带一提：这套测试真的抓出了 bug

写完测试跑第一遍，暴露出 3 个真实缺陷，全部修掉了：

1. `ResultCode.BUSINESS_ERROR` 原来是 **500** —— 和「服务端崩了」混在一起，排查问题时无法区分"业务规则拦截"和"代码出错"。改成 **422**。
2. 下单接口里「不能购买自己的商品」返回 **500**，语义上应该是 **403**；「商品当前不可购买」应该是 **409**。
3. `Result.isSuccess()` 被 Jackson 当成属性序列化了，响应体里多出一个冗余的 `success` 字段，加 `@JsonIgnore` 去掉。

**这个故事本身就是很好的面试素材**：它说明测试不是走过场，而是真的能发现你自己看代码看不出来的问题。

补接口层集成测试时又抓出一个**设计不一致**：管理端「封禁用户」接口的 `status` 是用 `@RequestParam` 传的，而项目里其他所有写接口都是 JSON body。写测试时我下意识按 body 传，结果被当成「缺少必填参数」返回 400 —— 也就是说，**这个接口对调用方是反直觉的**。它没坏，但暴露了 API 风格不统一。

我没有顺手改它（改接口签名会牵动前端），而是把这个认知写进了测试注释里：

```java
// 注意 status 是 @RequestParam 而不是请求体，写成 JSON body 会被当成缺少参数而返回 400
```

**面试时这是个很好的「权衡」素材**：发现不一致 → 评估改动成本 → 决定不在收尾阶段动它 → 但用注释和测试把行为固定下来，避免下一个人再踩。这比"我发现问题就改"更接近真实工程。

## 11. 订单超时自动取消：定时任务里最容易踩的三个坑

### 面试官怎么问

> "下单后商品就锁定了，如果卖家一直不确认呢？"

### 先讲清问题

买家下单后，商品从 `ON_SALE` 变成 `LOCKED`。如果卖家一直不处理，这笔订单会永远挂在「待卖家确认」，商品也永远回不到在售 —— 相当于这件商品被一个**僵尸订单**占死了，其他人都买不了。

所以需要一个定时任务，定期把这类订单清理掉。

### 坑一：用 fixedRate 会导致任务重叠

```java
// ❌ 固定频率触发，不管上一轮跑完没有
@Scheduled(fixedRate = 60000)

// ✅ 上一轮结束后再等 N 毫秒，天然不会重叠
@Scheduled(fixedDelay = 60000)
```

数据量上来后，`fixedRate` 会出现两个线程同时处理同一批订单。虽然因为后面要讲的 CAS，不会造成数据错乱，但白白产生重复查询和锁竞争。

**如果面试官追问**："那多台机器部署呢？`fixedDelay` 只能保证单机不重叠。"
→ 承认这是已知局限：多实例下每个实例都会扫到同一批订单。取消动作本身是 CAS 的，不会写坏数据，但会产生无谓的重复查询。要彻底解决得加分布式锁（Redis SETNX / ShedLock）。**这个项目是单机部署，所以我没引入这个复杂度** —— 主动说清楚边界，比硬说自己做了分布式锁要好。

### 坑二：定时任务和用户操作会竞争

这是整个功能最容易出错的地方。场景：定时任务刚查出「订单 X 是 CREATED 状态，超时了」，准备取消。就在同一瞬间，卖家点了「确认」。

如果代码是「先查后改」：

```java
// ❌ 中间可能被别人改掉
if (order.getStatus().equals("CREATED")) {
    order.setStatus("CANCELLED");
    orderMapper.updateById(order);
}
```

结果就是：**一笔卖家已经确认的订单被系统取消了**。卖家莫名其妙，买家也莫名其妙。

正确做法是把判断和修改压成一条 SQL，也就是 CAS：

```java
@Update("UPDATE product_order SET status = 'CANCELLED', "
        + "cancel_time = #{cancelTime}, cancel_reason = #{reason} "
        + "WHERE id = #{id} AND status = #{expect}")
int casCancel(...);
```

`WHERE status = #{expect}` 就是「只有此刻仍是这个状态才允许改」。两边同时发起，只有一方能拿到影响行数 1，另一方是 0 —— 拿到 0 的一方静默放弃即可。

**注意影响行数为 0 不是错误**，是正常的竞争结果，所以代码里是 `return false` 而不是抛异常：

```java
int updated = orderMapper.casCancel(order.getId(), from.name(), now, TIMEOUT_REASON);
if (updated == 0) {
    return false;   // 被用户抢先处理了，跳过即可
}
```

**还有一个细节**：取消成功后才去释放商品，且商品那边同样用 CAS：

```java
productMapper.casUpdateStatus(order.getProductId(),
        ProductStatus.LOCKED.name(), ProductStatus.ON_SALE.name());
```

如果订单没取消成功（`return false`），**绝对不能**去动商品 —— 否则会把一笔正常订单对应的在售商品错误地释放出去，造成超卖。这是我在单测里专门断言的一条。

### 坑三：@Transactional 在同类内部调用会失效

这个坑很隐蔽。我原本想把它写成 `OrderServiceImpl` 里的一个私有方法，但那样事务注解会被**静默忽略**：

```java
@Service
public class OrderServiceImpl {
    public void cancelTimeoutOrders() {
        cancelOne(order);   // ❌ 走的是 this，不经过代理，@Transactional 失效
    }

    @Transactional
    private void cancelOne(ProductOrder order) { ... }
}
```

原因是 Spring 的 `@Transactional` 基于动态代理：外部调用拿到的是代理对象，但**类内部的方法调用走的是 `this`，绕过了代理**。

所以我把单笔取消抽成了一个独立的 Bean：

```java
@Component
public class OrderTimeoutCanceller {
    @Transactional(rollbackFor = Exception.class)
    public boolean cancelOne(ProductOrder order) { ... }
}
```

调用方注入的是代理对象，事务才真正生效。

**为什么必须每笔订单独立事务，而不是整批一个事务？**
如果整批共用一个事务，第 50 笔出问题时，前面 49 笔已经成功取消的会被**一起回滚**，下一轮扫描还得从头再来 —— 白干活。每笔独立事务则互不影响，单笔失败只是这一笔留到下一轮重试。

这一点我在单测里直接断言了：3 笔订单中间那笔抛异常，最终必须取消成功 2 笔。

### 顺带两个设计决定

**1. 超时取消不扣信用分。** 用户主动取消是有罚分的（卖家确认后买家反悔扣 3 分），但超时是系统行为 —— 可能是卖家一直不响应，也可能是双方都忘了。归咎于任何一方都不公平，所以不加惩罚。

**2. 两类订单用不同的时间戳起算。**

```sql
WHERE (status = 'CREATED'   AND create_time  < #{deadline})
   OR (status = 'CONFIRMED' AND confirm_time < #{deadline})
```

`CREATED` 是「卖家一直不确认」，从下单时间算；`CONFIRMED` 是「卖家确认了但交易一直没完成」，从确认时间算。都统一用 `create_time` 的话，一笔早就确认的订单会被过早取消。

### 怎么演示

默认超时是 30 分钟，等它太久了。用短超时配置启动，一分多钟就能看到效果：

```bash
java -jar target/campus-market-1.0.0.jar --spring.profiles.active=local \
     --app.order.timeout-minutes=1 \
     --app.order.scan-interval-ms=5000 \
     --app.order.initial-delay-ms=5000

bash scripts/timeout-demo.sh
```

> 别把 `timeout-minutes` 设成 0 —— 那样订单创建后一两秒就被扫走，
> 「下单后商品应该被锁定」这个中间状态根本来不及观察，看起来像是功能坏了。

脚本会自动发布商品 → 下单 → 等定时任务清理 → 校验订单变 CANCELLED、商品回到 ON_SALE、信用分未被扣、商品可被重新下单。

## 12. 如果面试官问「这个项目有什么不足」

**千万不要说"没什么不足"**。主动承认局限，比硬撑显得成熟。可以这么答：

> 有几个我知道但没做的点：
>
> 1. **没有接口幂等**。用户连点两次"下单"，第二次会因为商品已 LOCKED 而失败，但返回的提示是"商品已被抢先下单"，语义不太对。更规范的做法是前端生成 `requestId`，服务端用 Redis 做幂等表。
> 2. **超时清理是单机定时任务**。多实例部署时每个实例都会扫到同一批订单，需要加分布式锁（Redis SETNX / ShedLock）才能避免重复执行。数据不会错乱（取消动作是 CAS 的），但有无谓的重复查询。
> 3. **搜索用的是 `LIKE '%关键词%'`**，前置通配符会让索引失效。数据量上来要换 Elasticsearch。
> 4. **浏览量直接打数据库**。高频商品会有写压力，应该走 Redis 计数再定时落库。
> 5. **集成测试跑在 H2 上，不是真 MySQL**。53 项测试里那 28 项接口层测试用的是 H2 的 MySQL 兼容模式，图的是「不装数据库也能跑、CI 友好」。代价是方言差异：H2 对 `ON DUPLICATE KEY UPDATE`、某些窗口函数、索引行为都和真 MySQL 不完全一致 —— 所以我还额外保留了 108 项打真实 MySQL 的冒烟脚本兜底。更彻底的做法是用 Testcontainers 起一个真的 MySQL 容器，但那要求 CI 环境能跑 Docker，我评估后觉得对这个项目性价比不高。
> 6. **接口风格有一处不统一**。管理端「封禁用户」的 `status` 走的是 query 参数，其余写接口都是 JSON body。没改是怕牵动前端，只在测试里把行为固定住了。

这样答的好处是：**你既展示了对自己代码的清醒认知，又把话题引到了 Redis / 消息队列 / ES 这些你准备好的知识点上。**
